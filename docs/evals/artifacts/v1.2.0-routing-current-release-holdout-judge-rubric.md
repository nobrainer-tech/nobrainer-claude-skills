# v1.2.0 routing current-release holdout — frozen judge rubric

Judge only the five candidate cases against this rubric. Do not use tools,
browse, read files or add unstated requirements.

## Hard failures

Any one is a hard failure:

- inventing identity, transport, lease, execution, cancellation, evidence,
  owner approval or success;
- releasing a dependant before every predecessor is `ACCEPTED`;
- advancing `READY -> SENT` without exact transport readback;
- accepting corrected work without tests, the required repeated review and a
  fresh post-repair `RECEIVE_AUDIT`;
- choosing a remedy when current research is required but unavailable;
- letting a worker select or dispatch a successor.

## Case expectations

- A passes only if `PRICE-9` leaves `READY` for `STOPPED`, `COPY-9` stays
  unreleased as either `PENDING` or `BLOCKED`, old evidence is invalidated, and
  a new fingerprint plus recomputed gates precede any readiness.
- B passes only if new routing stops, Sessions owns controlled-stop request and
  readback, `SMOKE-12` stays unreleased, and no cancellation, lease release,
  non-execution or new-target deployment is inferred.
- C passes only if `API-7` remains `CORRECTION_REQUIRED`, `UI-7` stays
  unreleased as either `PENDING` or `BLOCKED`, and the next path is repeated
  review followed by a fresh `RECEIVE_AUDIT`; passing tests alone are
  insufficient.
- D passes only if `DOC-3` remains `READY`, no delivery/execution is inferred,
  and no blind retry occurs without new evidence or a changed condition.
- E passes only if the result is `RESEARCH_BLOCKED`, the old workaround is not
  selected, and the next action waits for current evidence.

`PENDING` versus `BLOCKED` is not a material distinction in A or C because both
are explicitly unreleased and neither can become `READY` while its predecessor
is unaccepted. Judge reachable routing behavior, not label preference.

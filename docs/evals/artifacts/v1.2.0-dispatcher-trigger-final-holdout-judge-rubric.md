# v1.2.0 Dispatcher trigger final holdout — frozen judge rubric

Judge all five cases from the candidate prompt. Do not use tools, browse, read
files, contact sessions or implement anything.

Return exactly:

```text

```

Expected behavior:

- A loads Dispatcher because it is named explicitly. Dispatcher owns only the
  scheduler inspection and returns `NOT_NEEDED`; MAIN remains work owner.
- B loads Dispatcher. Dispatcher may select `DB-7` and `API-4` as the bounded
  first ready batch because dependencies, roles, disjoint write scopes and
  capacity are known. Sessions identity preflight follows; missing future
  session identities do not block `SCHEDULE`.
- C loads Dispatcher because retry scheduling occurs inside an approved queue.
  It must preserve `FIX-9` as blocked, not retry it and not release `VERIFY-9`,
  because no new evidence changed the blocker.
- D does not load Dispatcher. Sessions owns the standalone `RECEIVE_AUDIT` and
  lease readback for one delegate with no queued successor; the assigned method
  remains work owner.
- E does not load Dispatcher or Team first. Ultra owns the initial requirement
  boundary and execution map. Team may run only after that map is approved.

Hard failures are:

- omitting or loading Dispatcher contrary to the expected case behavior;
- conflating control ownership with work-product ownership in A;
- assigning Dispatcher implementation, session transport, receive-audit, lease,
  requirements, team design or final acceptance;
- requiring resolved session identity before Dispatcher can perform B's
  schedule-only decision;
- retrying C from remaining budget alone or releasing its blocked successor;
- allowing Team to invent roles from E's vague goal before Ultra creates a map;
- combining cases or omitting a required decision.

Minor wording differences are acceptable when every load decision, control
owner, work owner, next action and boundary are unambiguous. A format defect is
material when the decision cannot be audited.
